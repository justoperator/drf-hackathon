# Завдання команди — паркінг місця на рівні

Цей файл керує роботою учасників і ШІ-агентів.

## Як ШІ запускається

Коли користувач пише лише ім’я, наприклад `Юрій`, агент:

1. знаходить у секції цього ім’я перше невиконане завдання;
2. читає задачі та правила в `AGENT.md`;
3. працює тільки у файлах відповідної ролі;
4. робить один маленький готовий результат;
5. перевіряє його;
6. робить один коміт у гілку `testing`;
7. робить короткий опис того, що змінено і чому;
8. позначає завдання `[x]` в `tasks.md` тільки після успішної перевірки;
9. дописує короткий запис у журнал `AGENT.md`;
10. зупиняється і не бере наступне завдання за один запуск.

При зміні спільного коду обов’язково попередьте у коментарі до коміту або у
журналі, чий файл зачеплено.

## Загальні правила для кожного ШІ

- Максимальна практична безпека: без відкритого доступу до чужих заявок,
  підміни `owner`/`status`, SQL-гонок, traceback-розкриттів або небезпечних комітів.
- Код має бути простим, коротким і читабельним; формати PEP 8 обов’язкові.
- Не робіть великі переробки «про запас». Виконайте одне завдання на коміт.
- Не змінюйте коду інші ролі без реальної потреби.
- Не комітьте `.venv/`, `db.sqlite3`, `__pycache__/`, секрети чи скомпільовані файли.
- Перед комітом запустіть `python manage.py check` і потрібну конкретну перевірку.
- Не пуште у `main`. Усі коміти йдуть лише у `testing`.
- Не прибирайте зміни інших учасників командами `reset --hard` або `checkout`.
- Після зміни поясніть максимально просто: що зробили, у чому небезпека і як
  перевіряли. Пояснення має бути 3–7 коротких речень.

## Команди Git для агента

Перед початком завдання:

```powershell
git switch testing
git pull --ff-only origin testing
git status
```

Після перевірки:

```powershell
git add <дозволені-файли>
git diff --cached
git commit -m "Зрозумілий опис маленької зміни"
git push origin testing
```

Не використовувати `git push origin main`, `git reset --hard` і примусове
переписування історії.

Для кожного завдання створюйте окремий маленький коміт. Приклад підпису:

```text
feat(parking): add positive quantity validation
fix(permissions): hide other users requests
test(race): verify one successful confirm
docs(parking): update curl scenario
```

## Як називати коміти

Усі коміти мають виглядати так, ніби їх писав справжній користувач-партнер,
коротко описуючи конкретну зміну людською мовою.

Обов’язкові правила для назви коміту:

1. Писати нормальними словами від першої особи-помовчуванням не потрібно.
2. Не використовувати формальні префікси типу `feat:`, `fix:`, `docs:`,
   автоматичні посади агентові або слова `AI`, `agent`, `бот`, `assistant`.
3. Не використовувати назви типу «завдання 3», «T4», «оновлення файлу»,
   «зробив завдання» чи довгі списки змін.
4. Назва має починатися з дієслова і називати одну конкретну зміну:
   «Додано захист для чужих заявок», «Виправлено перевірку кількості місць».
5. Не копіювати шаблонну назву для кожного коміту. Міняйте фразу під реальний
   результат, зберігайте українську мову та стиль звичайної команди.
6. Назва має бути зрозумілою людині без читання коду:
   що саме змінилося і для чого.
7. Коміт без реальної перевірки називати так, ніби роботу завершено, заборонено.

Не використовувати приклади нижче як копіпасту. Вони показують стиль:

```text
Додано перевірку власника заявки
Виправлено від’ємну кількість місць
Додано endpoint підтвердження заявок
Налаштовано автоматичне відновлення паркінгу
Додано тест повторного скасування
Оновлено інструкцію для запуска атаки
```

## Черга виконання завдань

Завдання потрібно виконувати блоками. У межах одного блока ролі можуть працювати
паралельно, але кожен агент бере лише одне завдання за запуск.

### Блок 1 — спільна основа

1. Данило T1–T9: моделі, стани і обмеження бази.
2. Олег T1–T10: seed, тестові акаунти, каталог і `contract.json`.
3. Після міграції та seed усі учасники оновлюють гілку `testing`.

### Блок 2 — API і доступ

Можна починати одночасно після Блоку 1:

1. Дмитро T1–T12: права, автентифікація та фільтрація власних заявок.
2. Святослав T1–T12: serializer-и, router, viewsets і обгортки actions.
3. Юрій T1–T12: atomic-сервіси `confirm` і `cancel`.

Юрій може почати T1–T6 після появи стабільних моделей. Views і права мають бути
достатньо готові для перевірки повного HTTP-сценарію.

### Блок 3 — узгодження контракту

Після Блоків 1–2 Олег виконує T11–T12:

1. оновити README і curl-сценарій;
2. перевірити seed і реальний API.

### Блок 4 — перевірка порога

Усі ролі разом запускають контрольну точку:

```powershell
python tools/attack_open.py --only 1,2,3,7,8,18,19
```

Якщо рядки не зелені, спочатку виправляють відповідні ролі в поточній черзі:

- рядки 1 і 2 — API і Доступ;
- рядки 3 і 7–12 — API і Доступ;
- рядки 18–19 — Стійкість;
- seed або поля contract — Моделі/Олег.

### Блок 5 — стійкість і гонки

Після зеленої контрольної точки:

1. Юрій повторно перевіряє і виправляє гонки;
2. Дмитро перевіряє ряди атаки після зміни сервісів;
3. Святослав перевіряє HTTP-коди і actions;
4. Олег перевіряє відновлення seed і contract.

Потім команда запускає повну відкриту карту й обидві гонки.
