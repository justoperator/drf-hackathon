# AGENT.md

Цей файл є спільним контекстом для агентів і людей, які працюють над проєктом.
Перед змінами прочитайте його та `README.md`. Після завершення роботи допишіть
короткий запис у розділ **Журнал агентів**.

## Призначення проєкту

Це навчальний API-спринт на Django REST Framework. Домен ще не обрано:
потрібно реалізувати каталог обмеженого ресурсу та заявки користувачів на цей
ресурс, а потім витримати перевірки доступу й одночасні `confirm`/`cancel`.

Поточний стан репозиторію — стартовий скелет. Більшість файлів `api/` містить
лише docstring і заготовлені імпорти; не вважайте API вже реалізованим.

## Технічний стек і запуск

- Python 3.10+.
- Django `>=5.1,<7`, Django REST Framework `>=3.15`,
  Simple JWT `>=5.3`.
- SQLite у `config/settings.py`; timeout запису — 20 секунд,
  `transaction_mode = "IMMEDIATE"`.
- Мова/часова зона: `uk` / `Europe/Kyiv`.
- JWT access token живе 8 годин.

Windows:

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
python manage.py migrate
python manage.py seed_attack
python manage.py runserver
```

Файл `db.sqlite3` і віртуальні середовища не комітяться. Після змін моделей
потрібна Django-міграція.

## Архітектура та межі відповідальності

| Компонент | Відповідальність |
|---|---|
| `api/models.py` | Модель каталогу, модель заявки, стани й обмеження БД |
| `api/serializers.py` | Валідація вхідних даних і формат JSON; `owner` та `status` не задаються клієнтом |
| `api/views.py` | ViewSet-и, queryset, `confirm`/`cancel`; без розрахунку залишку |
| `api/services.py` | Уся зміна залишку та стану заявки в `transaction.atomic()` |
| `api/permissions.py` | Доступ до власних заявок; список обов’язково фільтрується в `get_queryset` |
| `api/urls.py` | DRF router і адреси ресурсів |
| `api/management/commands/seed_attack.py` | Ідемпотентні тестові користувачі та каталог |
| `api/admin.py` | Реєстрація моделей для огляду під час атаки |
| `contract.json` | Машиночитаний контракт для `tools/attack_open.py` і `tools/race.py` |
| `README.md` | Інструкція команди та curl-сценарій |

Не переносіть бізнес-логіку з `services.py` у view або serializer. Якщо змінюєте
адреси чи назви JSON-полів, одночасно оновіть `contract.json`, README і скрипти,
якщо це необхідно.

## Доменний контракт

Після вибору домену мають існувати:

1. Елемент каталогу з числовим невід’ємним залишком (`PositiveIntegerField`).
2. Заявка з `owner` (FK на `User`), FK на елемент каталогу, додатною
   `quantity` та `status`.
3. Рівно три стани заявки: `draft`, `confirmed`, `cancelled`.
4. `CheckConstraint` для невід’ємного залишку. Це страховка, а не механізм
   конкурентного захисту.

У `contract.json` обов’язково узгодити:

- `items` — endpoint каталогу зі слешем;
- `orders` — endpoint заявок зі слешем;
- `item_field`, `qty_field`, `left_field`;
- `order_extra` для інших обов’язкових полів;
- `race_item` — ID елемента із залишком рівно `1`;
- `users` — ті самі паролі, що й у `seed_attack`.

Початковий `contract.json` використовує приклад `bikes`/`rentals`, але це ще не
доводить, що домен велосипедів реалізовано.

## Інваріанти та конкурентність

- Ресурс вважається зайнятим тоді й лише тоді, коли заявка має `confirmed`.
- `confirm` дозволений лише власнику заявки зі станом `draft`; він атомарно
  резервує `quantity` і переводить заявку в `confirmed`.
- `cancel` дозволений лише власнику заявки зі станом `confirmed`; він атомарно
  повертає `quantity` і переводить заявку в `cancelled`.
- Повторні або недозволені переходи стану мають повертати `409`, а помилки
  валідації — `400`.
- Умова зменшення залишку повинна бути частиною SQL `UPDATE` (наприклад,
  `available__gte=quantity`), а результат оновлення треба перевіряти.
- Усі зміни заявки й залишку виконувати в одній `transaction.atomic()`.
- Ні одна заявка не може двічі зменшити або збільшити залишок.
- При конкурентному підтвердженні однієї заявки успішним має бути рівно один
  запит; для різних заявок успішні лише ті, на які вистачає залишку; відповіді
  не повинні бути `5xx`.

## Очікуваний доступ

- Каталог можна читати без JWT.
- Список заявок і створення заявки потребують автентифікації.
- Власник заявки може бачити та змінювати лише свою заявку.
- `owner` встановлюється з `request.user`, а не з тіла запиту.
- `status` встановлюється сервером і є read-only.
- Перевірка об’єкта не замінює фільтрацію списку: `get_queryset` має повертати
  лише заявки поточного користувача.
- `/admin/` не повинен приймати очевидні тестові паролі `admin` або `1234`.

## Перевірка

Після запуску сервера:

```powershell
python tools/attack_open.py
python tools/attack_open.py --only 18,19,21
python tools/race.py --item <id> --orders 10
```

Перед повторною гонкою для `race_item` запустіть `python manage.py seed_attack`,
оскільки seed має відновлювати початкові залишки через `update_or_create`.
Зелене виконання гонки не є доказом: повторіть її кілька разів.

Мінімальна перевірка коду перед передачею:

```powershell
python manage.py check
python manage.py makemigrations --check --dry-run
```

## Правила роботи агентів

1. Зробіть вузьку зміну відповідно до ролі; не переписуйте чужі файли без
   необхідності.
2. Перед редагуванням перевірте фактичний стан файлу — шаблонні TODO можуть уже
   бути замінені іншим агентом.
3. Не додавайте секрети, реальні паролі чи згенеровану базу даних.
4. Нові міграції, змінені поля, endpoint-и й контракт мають бути узгоджені між
   собою.
5. Після тестів зафіксуйте результат у журналі нижче: дата, агент/роль,
   файли, що змінено, перевірки та незавершені питання.
6. Не видаляйте записи інших агентів; додавайте новий запис унизу.

